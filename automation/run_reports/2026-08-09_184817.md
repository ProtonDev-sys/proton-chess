# Same-key transposition-table replacement

- Time: `2026-08-09T18:48:17+01:00`
- Branch: `agent/search-strength-1`
- Base: `origin/main` at `6d25433`
- Result: kept as a bounded search-quality repair; no Elo gain claimed

## Problem

`Search::store` protected a much deeper same-key TT result from a shallow non-exact write only when the incoming move was null. Normal alpha-beta, quiescence and ProbCut writes usually carry a move, so a shallow bound could replace a deep score, static evaluation, depth and bound merely to refresh move ordering.

The adjacent different-key case could also retain the evicted position's move when the incoming replacement had no move.

## Change

- Decoupled same-key move refresh from replacement of the stored search result.
- Retained the existing two-ply replacement margin: non-exact writes at least three plies shallower preserve the deeper tuple; exact and near-depth writes replace it.
- Refresh the generation of a retained same-key entry.
- Preserve an existing same-key move when the accepted write has no move.
- Clear an unrelated move when a different key replaces a bucket entry with a null move.
- Added a test-only friend peer rather than a production debug API or preprocessor access hack.

## Focused regressions

- Depth-10 lower bound followed by a depth-2 upper bound retains score, static evaluation, depth and bound while refreshing the move.
- A rejected depth-7 null-move write against depth 10 retains both the full value tuple and the existing move, locking the first protected depth boundary.
- A depth-8 write replaces depth 10 at the existing margin boundary.
- A shallow exact write replaces the value tuple and preserves the prior move when its own move is null.
- A rejected write refreshes an older entry into the current generation without discarding its deep tuple.
- Five keys forced into one Hash-1 bucket prove that a different-key null-move replacement does not inherit the evicted move.

## Fixed-depth evidence

Baseline executable: `687e31758ba3f4a31a2a0bc74eedee68548adeca602fa7aa500b221a11578a28`.

Candidate executable: `1123e22a742f70e18ba04012293f313ad17e62f70a4830ec91bd6b8e67c791e7`.

All 200 pinned UHO positions were searched from a fresh game at depth 9 with book, human style and strength limiting disabled.

- Hash 1: baseline 25,217,233 nodes; candidate 25,165,505 nodes (`-0.205%`); same best move on 193/200 positions.
- Hash 64: baseline 25,629,401 nodes; candidate 25,503,264 nodes (`-0.492%`); same best move on 194/200 positions.

The patch changes search behavior and is not described as behavior-preserving.

The exact benchmark was an inline Python UCI harness. For each binary and hash size it launched one process, sent `uci`, set `Hash`, `UseBook=false`, `HumanStyle=false` and `UCI_LimitStrength=false`, then sent `ucinewgame`, `position fen <each non-comment EPD line>` and `go depth 9` for every suite position. It summed the final depth-9 `nodes` field and compared best moves. The harness invocation used these resolved inputs:

```text
baseline=build/bench/search_strength_1_baseline.exe
candidate=build/bench/tt_replacement_candidate.exe
openings=openings/uho_lichess_4852_v1_200.epd
hash_mb=1,64
depth=9
```

The generated binaries and raw rows lived under ignored `build/bench`; only this summary is retained. The binary hashes above make the inputs identifiable, but this is supporting search evidence rather than a release benchmark artifact.

## Paired A/B evidence

The repository runner used the pinned UHO suite, color-swapped pairs, one process per game, Hash 16, 50 ms/move, 240-ply cap and seed `20260809`. Both binaries ran through their zero-loss Elo-3000 profile.

The exact 200-game command was:

```powershell
python tools/estimate_elo.py build/bench/tt_replacement_candidate.exe build/bench/search_strength_1_baseline.exe --proton-elo 3000 --opponent-elo 3000 --games 200 --move-time 0.05 --max-plies 240 --hash 16 --seed 20260809 --openings openings/uho_lichess_4852_v1_200.epd --json build/bench/tt_ab_screen_200.json
```

The 400-game command was identical except for `--games 400` and output `build/bench/tt_ab_final_400.json`.

- 20-game smoke: 7 wins, 4 draws, 9 losses; all games legal and complete.
- 200-game early look: 70 wins, 69 draws, 61 losses; score `0.5225`; estimated delta `+15.65 Elo`; exact paired `p_gain=0.1938`; inconclusive at alpha `0.005`.
- 400-game final look: 145 wins, 111 draws, 144 losses; score `0.50125`; estimated delta `+0.87 Elo`; exact paired `p_gain=0.5`, `p_regression=0.5511`; inconclusive at alpha `0.045`.

The candidate path set a deterministic per-game `HumanSeed`, but the runner's Stockfish-oriented second-engine path did not set `HumanSeed` on the baseline Proton binary. Book use was bypassed by limited mode and `HumanStyle` defaulted false, but the baseline could still use its random-device seed when choosing among exactly equal zero-loss alternatives. The match therefore does not strictly isolate the patch or reproduce every baseline choice from seed `20260809`; it is retained only as a gross regression screen. It proves no Elo gain. The change is kept for its directly tested replacement semantics and small fixed-depth node reduction.

## Limits

- The final A/B sample is statistically inconclusive and must not be cited as an Elo improvement.
- The A/B seed asymmetry makes it weaker than a generic, identically configured full-strength engine comparison; future strength runs need a dedicated A/B harness.
- The TT move may be newer than the retained value. Any later singular-extension implementation must track that association explicitly before treating the move and bound as one result.
- Full Elo calibration and the pinned Stockfish-3000 certification remain outstanding.
